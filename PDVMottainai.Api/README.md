# API local do PDV Mottainai

Projeto ASP.NET Core independente da interface desktop, que fica no repositório [Mottainai-POS_front](https://github.com/Mottainai-One/mottainai-POS_front). Base URL padrão: `http://127.0.0.1:5097`. Execute `dotnet run --project PDVMottainai.Api` no Windows. A API escuta loopback. A especificação está em `docs/API-POS.openapi.yaml`; ela não é servida por uma rota HTTP.

Configuração é feita por variáveis de ambiente. `Api__Port` define a porta; `Api__TerminalId` é obrigatório para login offline vinculado ao terminal. `Firebase__ProjectId` e `ConnectionStrings__Operational` configuram o Firebase Auth e PostgreSQL operacional; nunca use a conexão analítica. Credenciais ficam em secret store/ambiente protegido, nunca em appsettings versionado. O login e a preparação do grant usam Firebase/PostgreSQL quando configurados.

O SQLite local persiste catálogo com preços normais, sessão local, turnos, movimentos, rascunhos, pedidos de aprovação e fila de sincronização. Promoções Mottainai não fazem parte do cache offline. Para usar uma promoção online, o operador primeiro valida a conta em `POST /customers/search`, e o produto/venda deve receber o `customerId` validado dentro da janela local de 15 minutos; sem validação, aplica-se o preço normal. A abertura e o fechamento online usam PostgreSQL; sem conexão, o fechamento falha e mantém o turno aberto. Antes de habilitar as gravações/replay, aplique no banco operacional as atualizações `update_existing_api_rpa.sql` e `update_existing_pos_api.sql` do repositório [Mottainai-Banco-Operacional](https://github.com/Mottainai-One/Mottainai-Banco-Operacional); não use o banco analítico. Os itens sincronizados permanecem `DRAFT` e não reservam lote/estoque. O fechamento recusa movimentos pendentes e calcula pagamentos em dinheiro já concluídos no PostgreSQL. Refresh/logout do `staff_session` também é enfileirado para reconciliação.

## Aprovações do gerente

`POST /approvals` cria offline um pedido `CANCEL_PURCHASE`, `CANCEL_PRODUCT`, `REFUND`, `RETURN` ou `SPECIAL_DISCOUNT`; `GET /approvals/{requestId}` consulta o estado local. O outbox sincroniza os pedidos com `mottainai_operational`. Cancelamentos usam `pos_cancel_request` e a decisão do gerente executa o cancelamento no banco. Descontos especiais aprovados alteram o preço do item enquanto a venda ainda está em `DRAFT`. Estorno e devolução ficam registrados como aprovados/rejeitados; o sistema não contém integração de adquirente/pagamentos ou execução de devolução de estoque.

Para notificação e decisão pelo app Mottainai Operacional, configure no processo da API `Firebase__PosApprovalFunctionUrl` com a URL HTTPS da Cloud Function `posApprovalBridge` e `Firebase__PosApprovalApiSecret` com o mesmo segredo configurado no Firebase Secret Manager (`POS_APPROVAL_API_SECRET`). A Cloud Function envia o push FCM e grava uma notificação na inbox Redis para cada gerente/dono ativo da loja. Configure também `NOTIFICATION_PUBLISHER_SECRET` na API Redis e `REDIS_NOTIFICATION_API_URL` mais `REDIS_NOTIFICATION_API_SECRET` no ambiente da Cloud Function; a URL deve apontar para `POST /internal/v1/notifications` por uma rota HTTPS acessível à Cloud Function. A API local do PDV consulta as decisões como antes. O app precisa ter token FCM registrado para receber push; a inbox Redis funciona mesmo sem token. Publique também as regras e os índices Firestore do repositório Mobile Operacional. Mantenha os segredos fora do app, dos arquivos versionados e dos logs.

As 24 rotas originais permanecem preservadas. As duas rotas de aprovação são endpoints auxiliares do fluxo do gerente e não ocupam nem alteram a posição 25 da lista original.
